## 3. 일러스트 스타일 (새 레퍼런스 기준, 2026-10-09 사용자 결정)

근거: 사용자가 준 32초 모션 영상을 프레임으로 본 결과. 이전의 굵은 검정 외곽선·플랫 컬러 화풍(참고 채널 방식)은 **쓰지 않는다.**

### 3-1. 화풍
- **배경은 장면마다 하나**: ① **종이**(따뜻하거나 차가운 회백색 `paper_base`, 가는 연필 스케치 선) ② **밤**(`night_top`→`night_bottom` 짙은 바탕, 은은한 비네팅) ③ **노을 하늘**(`dusk_stops` 3색 그라데이션). **각 색은 그 영상의 팔레트에서 가져온다(3-5).** 영상 전체에서 종이·밤·노을을 섞는다(한쪽이 절반을 넘지 않게).
- **선**: 얇은 손그림 선, 선 굵기 2.5~4px(주인공만 6px까지), 곡선은 약간 흔들리게. **모든 물체에 균일한 굵은 검정 외곽선을 두르지 않는다.** 종이 장면은 팔레트의 먹색(`paper_ink`), 밤 장면은 팔레트의 빛나는 선(`night_line`)과 글로우(`night_glow`).
- **음영**: 큰 형태에는 부드러운 그라데이션과 빛(글로우), 질감은 해칭(짧은 평행선). 색은 풍부하되 조화롭게, **그 영상 팔레트의 강조색 4개를 주로 쓴다(3-5). 보라·마젠타·주황을 기본값으로 쓰지 않는다.** 흰 배경 위 네온은 쓰지 않는다.
- **인물**: 단순하지만 품위 있는 실루엣, 점 눈, 절제된 표정, 다양한 피부색. 과장된 만화 표정·치비·3D·실사 금지.
- 그림(SVG) 안에는 글자·숫자를 그리지 않는다(간판 포함). 이름·숫자·말풍선은 3-6의 화면 텍스트 층으로 그림 위에 올린다.

### 3-2. 가운데 물체 규칙 (줌 전환의 핵심)
- 모든 그림은 **정중앙 (960, 500)에 둥근 물체 하나**를 둔다. 지름 170~260px, 밝은 중심(눈·렌즈·램프·접시·해·달·세포·시계·자물쇠 구멍 등). 중요한 것은 그 위에 놓지 않는다.
- **동심원과 방사선은 그리지 않는다**(2026-10-10 사용자 결정: 모든 그림에 반복돼 거슬림). 대신 장면 내용에 맞는 배경을 그림마다 따로 그린다(방, 풍경, 실험실, 현미경 시야, 노트, 타임라인 등). 이웃 컷과 같은 종류의 배경이 이어지지 않게 하고, 12컷 중 같은 종류는 2컷 이하로 한다(tools/art_spec_v4_backdrop.md).
- 가능하면 가운데 물체가 **다음 장면의 가운데 물체와 닮게** 한다(모양 겹치기 전환용, 4-3).
- 가운데 물체는 항상 빛이 깜빡이는 그룹(`mv-glint-core`)으로 만든다.
- 다른 시선 포인트는 왼쪽(x≈400)·오른쪽(x≈1500)에 둔다.

### 3-3. 소재와 연출 규칙
- **시대와 장소를 정확하게 재현한다**(복식, 건물). 단 사실 확인이 안 된 디테일은 그리지 않는다.
- **현대 일상 앵커**: 도입부와 결말에 현대인의 일상 장면을 넣는다. 영어권 시청자가 공감할 장면을 고르고, 주제가 한국일 때만 한국 장면.
- **은유를 시각화한다**: 대본의 비유를 그대로 그림으로 만든다(자물쇠=종 장벽, 저울=득실 등).
- 과학 개념은 같은 화풍의 도해로. 실존 인물 사실 묘사 금지. 실제 민족이 나오면 존엄하게. 죽음·식인·폭력은 직접 묘사하지 않고 분위기와 상징으로만.

### 3-4. 이미지 생성 프롬프트 템플릿 (영어, 생성 도구용)
```
soft 2D editorial illustration, thin hand-drawn ink lines, subtle hatching, soft gradients and gentle glow,
[paper background in palette paper_base | night background palette night_top->night_bottom | dusk gradient palette dusk_stops]  (colours from the video's palette, see 3-5),

```

### 3-5. 색 팔레트 (사용자 결정 2026-10-10: "색감이 보라색 아니면 주황색이다. 대본에 맞게 색감을 사용하자")

**문제**: 예전에는 모든 영상이 같은 색(보라 `#6b4bd6`, 마젠타 `#d64b9a`, 주황 `#d9694a`, 복숭아→분홍→보라 노을)으로 그려져서 주제와 상관없이 보라색 아니면 주황색이 나왔다. 기존 영상 그림에서 파랑 계열(남색 밤 포함) 약 35%, 주황 17~23%, 분홍·보라 약 10~14%였다(색상값을 세어 본 근사치).

**방식 (`tools/palettes.py`, 2026-10-10 구현)**
| 팔레트 | 어울리는 주제 | 느낌 |
|---|---|---|
| `ocean` | 바다·심해·강·물속 생물 | 청록·짙은 바다색 |
| `forest` | 숲·정글·습지·연못·식물·곤충 | 초록·이끼·흙갈색 |
| `desert` | 사막·사바나·고대 건조 지대·불 | 황토·호박색·적갈색(주황이 주제에 맞을 때만) |
| `ice` | 극지·빙하·겨울·고산 | 차가운 청회색 |
| `lab` | 과학·의학·현미경·화학·데이터 | 청록 + 호박색 포인트 |
| `history` | 역사·옛 도시·배·고문서·고고학 | 세피아·적갈색·금 |
| `space` | 우주·별·행성·물리·시간 | 짙은 남색 + 금색(보라는 성운일 때만) |
| `storm` | 전쟁·재난·무거운 주제·날씨·산업 | 회청색·탁한 금 |
| `body` | 인체·동물 생물학·사냥·음식 | 따뜻한 장미·갈색(보라 없음) |
| `sunset` | 노을·저녁·꿈·판타지에만 | 예전 보라·복숭아(기본값 아님) |
- 팔레트마다 종이(`paper_base`, `paper_ink`), 밤(`night_top`, `night_bottom`, `night_line`, `night_glow`), 노을(`dusk_stops` 3색, `dusk_ink`), 강조색 4개, 전환 워시 색 3개가 정해져 있다.
- **고르는 법**: 영상 `config.py`에 `PAL_DEFAULT = '<팔레트>'`(주제 전체의 기본)와 필요하면 `PAL = {'<art_theme>': '<팔레트>'}`(특정 장면만 다르게)를 쓴다. **대본이 무엇에 관한 것인지(장소·재료·분위기)로 고르고 취향으로 고르지 않는다. 한 영상에 최대 3개.** 예: 고래 사체(심해) → 기본 `ocean`, 포경선·옛 기록 장면 → `history`, 연구실 장면 → `lab`.
- `PLAN=1`로 `plan.json`을 만들면 모든 단위에 선택된 팔레트의 색이 `pal`로 들어가고, 그림 에이전트는 **`pal`의 색만** 배경·선·글로우·강조에 쓴다. 사람 피부, 동물 몸, 식물, 물 같은 사물의 고유한 색은 등장인물 시트를 따르되 팔레트와 어울리게 한다. 전환 워시(색 덮개)도 장면 팔레트를 따른다.
- `PAL_DEFAULT`가 없으면 예전 보라·복숭아(`sunset`)가 나오고 `PLAN=1`이 경고를 출력한다. **새 영상은 반드시 고른다.**
- **확인한 것**: 팔레트 10개가 로드되고 `plan.json`에 `pal`이 들어가는 것, 전환 워시 색이 팔레트에서 오는 것(코드 실행). **아직 확인하지 못한 것**: 새 팔레트로 실제 그림을 그려서 렌더한 결과(화면이 대본 분위기와 맞는지)는 새 영상을 만들어야 볼 수 있다. 기존 영상(`epomis-frog-hunter-v2`, `never-eat-human-meat-v4`)은 예전 색으로 그려져 있고 바뀌지 않았다. 색 값 자체는 내가 정한 것이며 마음에 안 들면 `palettes.py`에서 고친다.
- 썸네일(16장)도 같은 영상 팔레트의 색을 쓴다.


### 3-6. 화면 텍스트 (사용자 결정 2026-10-11: "이미지에 자막만 나오는 영상인데 대본에 따라 적절한 텍스트를 넣자")

그림 위에 대본에서 가져온 짧은 글자를 띄운다. **그림(SVG)에는 여전히 글자를 그리지 않고**, 빌더(`tools/build3.py`)가 그림 위에 HTML 층으로 올린다(철자가 정확하고 채널 폰트로 통일된다). 그림 에이전트가 단위마다 사이드카 JSON의 `labels`(0~3개)에 적는다(`tools/art_spec_v3.md` 끝).

| 종류 | 언제 | 모양 | 위치 |
|---|---|---|---|
| **이름 라벨** `name` | 화면에 보이는 생물·식물·장소·시대·물건의 이름을 그 단위 내레이션이 말할 때 | Fredoka 34px 둥근 알약. 종이 배경은 크림 바탕에 팔레트 먹색 글자·테두리, 밤·노을 배경은 반투명 검정 바탕에 흰 글자. 대상까지 얇은 선과 점 | 대상 옆 빈 곳 |
| **숫자 배지** `num` | 내레이션이 숫자·연도·크기·비율을 말할 때 | Fredoka 44px 대문자, 왼쪽에 팔레트 강조색 막대 | 화면 왼쪽 위 고정(가로 x 80·y 64, 세로 x 100·y 330) |
| **말풍선** `say` | 동물·이름 없는 사람·사물의 짧은 반응 | Patrick Hand 42px, 흰 바탕에 검은 테두리, 꼬리가 입을 가리킴 | 말하는 대상의 입 근처 |

**규칙**
1. **사실은 대본에서만**: 이름 라벨의 글자는 그 단위 내레이션에 있는 단어(대소문자 무시), 숫자 배지의 숫자는 그 단위에서 말한 숫자(숫자로 쓰든 "four", "two and a half", "a hundred"처럼 말로 하든)만 쓴다. 12-1 사실 확인을 거친 대본이므로 텍스트도 같은 근거를 따른다.
2. **말풍선은 사실을 말하지 않는다**: 4단어·24자 이하, 숫자 없음, 감정·반응만("Still here!", "Too hot...", "Hmm?"). 새 정보·주장·숫자를 넣지 않는다. **실존 인물에게는 쓰지 않는다**(지어낸 말을 실존 인물에게 붙이지 않음). 비꼬거나 조롱하지 않는다. 단위의 약 8분의 1에만(채널 결정).
3. **빈도(채널 결정)**: 단위의 약 절반에 텍스트 1개 이상. 이름 라벨은 새 생물·장소가 화면에 처음 나올 때(이웃 단위에서 같은 이름 반복 금지), 숫자 배지는 숫자를 말하는 단위마다. 칠판 장면에는 넣지 않는다(칠판이 이미 텍스트).
4. **시각**: 사이드카의 `word`(그 단위 대본의 단어)를 말하기 0.1초 전에 0.25초 팝인하고 컷 끝까지 유지한다. `word`가 없으면 컷 시작 약 0.4초 뒤. 숫자 배지는 왼쪽에서 0.3초 미끄러져 들어온다.
5. **카메라**: 이름 라벨·말풍선은 그림과 함께 움직이고(포커스 확대 때 대상을 따라감), 확대 중에도 글자 크기는 그대로 유지된다. 숫자 배지는 화면에 고정되어 카메라와 상관없다.
6. **안전 영역**: 가로 x 120~1800, y 80~860(자막 위), 오른쪽 위 로고 모서리(x 1660 이상, y 190 이하) 금지. 세로 x 100~940, y 300~1400. 얼굴·가운데 물체·대본이 말하는 부분을 가리지 않는다. 숫자 배지를 쓰는 단위는 그림의 왼쪽 위(약 640×160)에 중요한 것을 두지 않는다.
7. **글자 수**: 이름 28자, 숫자 배지 26자, 말풍선 24자 이하. 영어만.
8. **검사**: `labels_lib.check`가 빌드 때 1~7의 기계적 규칙(종류, 글자 수, 대본 단어·숫자 일치, 말풍선 단어 수·숫자, 안전 영역, 로고 모서리, 포커스 확대 후 라벨 위치)을 검사하고 하나라도 어기면 빌드를 멈춘다. 그림 에이전트는 `python3 tools/labelshot.py <슬러그> <미리보기 폴더> <uid…>`로 텍스트와 예시 자막을 얹은 미리보기를 보고 겹침을 고친다. 말풍선 내용이 사실을 담지 않는지, 라벨이 대상을 가리지 않는지는 기계로 검사할 수 없어 눈으로 확인한다.

## 4. 모션 규칙 (일러스트 장면)

### 4-1. 움직임 방식
- **카메라는 포커스 대상이 있을 때만 움직인다 (사용자 결정 2026-10-09)**: 컷마다 포커스 대상을 정하고, 대본에서 그 대상을 말하는 순간에 그 대상으로 확대한다. 포커스 대상이 없는 컷은 카메라를 **정지**한다. 목적 없이 살짝 줌인·줌아웃하는 움직임은 쓰지 않는다.
  - 이동 구조: **정지 → 한 번 부드럽게 이동(가속·감속, 약 1.2~2.6초) → 정지**. 이동 폭은 작게(배율 1.04 → 1.16~1.22). 같은 컷에서 여러 번 움직이지 않는다.
  - 컷마다 확대 위치나 배율이 점프하지 않는다. 다음 컷은 이전 컷이 끝난 구도에서 이어서 시작한다(같은 장면 안일 때).
  - **구현 (`build3.py`, 시험 렌더 프레임으로 확인)**: 그림마다 사이드카 JSON의 `focus [x, y, 배율]`(배율 1.5~2.2)과 `focus_word`(그 컷 대본에 그대로 있는 단어)를 둔다. 카메라는 그 단어를 말하기 **0.5초 전**에 1.4초 동안 가속·감속으로 대상까지 확대하고 컷이 끝날 때까지 정지한다. 가장자리 밖이 보이지 않게 확대 중심을 제한한다. 사이드카에 `focus`가 없으면 카메라는 정지한다. 본편 그림 123장 중 65장에 포커스가 있다.
  - 레퍼런스에서 확인한 패턴(1개 영상 측정): 큰 움직임은 짧게 몰려 있고 나머지는 정지에 가깝다. 변화량이 큰 구간은 0.5~1.2초였다.
- **장면 그림 전체의 부유(±12px)와 먼지 입자는 쓰지 않는다**. 카메라 정지 중에 화면이 미세하게 흔들리면 "의미 없는 흔들림"으로 보인다. 대신 장면 안 요소(인물·불꽃·빛)가 움직인다.
- **인물·사물 동작 (필수)**: 인물이 나오는 그림에는 `mv-` 그룹을 장면당 3~6개, 앞쪽 인물마다 최소 하나. 가운데 물체에는 `mv-glint-core`.
  | 그룹 | 동작 |
  |---|---|
  | `mv-breathe-*` 몸통 | 세로 1.00→1.03 (2.2초). 모든 인물의 몸에 |
  | `mv-nod-*` 머리 | ±3° 끄덕임 (1.8초, 축은 목) |
  | `mv-lean-*` 전신 | ±2° 기울임 (3초) |
  | `mv-arm-*` 팔 | ±14° (0.9초, 축은 어깨) |

### 4-3. 장면 나누기와 전환 (사용자 결정 2026-10-09)

**장면 나누기**
- **한 장면 = 새 그림 한 장 = 대본의 의미 단위 하나(보통 한두 문장), 최대 7초.** 보통 3~6초. 대본 문장이 길면 문장 안에서 의미가 바뀌는 곳에서 더 나눈다. 그림 장수에는 제한이 없다(20분 본편은 대략 230~260장, 대본 문장 수로 확정. 에포미스 18분 본편은 226장).
- 같은 그림을 확대·이동만 바꿔 여러 컷으로 쓰지 않는다(점프 컷으로 보여 끊기는 느낌이 난다). 컷이 바뀌면 그림이 바뀐다.
- 참고(레퍼런스 영상): 장면 길이 약 1.5~3초였다. Miya's Lab은 내레이션 영상이라 7초 이내로 정했다.

**전환 5종 (대본 내용에 맞춰 고른다. 같은 전환을 연속 두 번 쓰지 않는다)**
| 전환 | 모양 | 쓰는 곳 |
|---|---|---|
| **줌 전환** | 나가는 장면은 가운데 물체로 가속하며 확대(약 2.6배), 들어오는 장면은 가운데가 확대된 상태에서 시작해 감속하며 풀림 | 큰 구간 전환, "속으로 들어간다/들여다본다" 문장 |
| **모양 겹치기** | 앞뒤 그림의 가운데 물체가 닮게 그려져 있고, 그 모양이 이어지며 장면이 바뀜 | 앞뒤 가운데 물체가 비슷할 때(해→달, 렌즈→세포 등) |
| **슬라이드·와이프** | 그림이 옆이나 위로 밀려 나가고 다음이 들어옴 | 순서·나열·비교가 이어질 때 |
| **스케치→채색** | 선만 있는 그림이 잠깐 나온 뒤 색과 빛이 입혀짐 | 새 개념이 처음 나올 때 |
| **페이드** | 짧은 교차 페이드 | 같은 장소에서 시간만 지날 때 |
- 칠판 장면은 들어올 때와 나갈 때 하드컷(7-4).
- **구현 방식 (`tools/build3.py`, 시험 렌더로 확인)**: 줌 = 위 표대로. 모양 겹치기 = 들어오는 그림이 가운데 물체 위치(반지름 120px 원)에서 시작해 0.9초 동안 원형으로 퍼지며 열림(앞뒤 그림의 가운데 물체를 같은 위치·크기·색 계열로 그렸을 때만, **같은 장면 안에서만** 사용). 슬라이드 = 들어오는 그림이 오른쪽에서 0.7초 밀려 들어오고 나가는 그림은 화면 폭의 18%만 왼쪽으로 밀림. 페이드 = 0.6초 교차. **스케치→채색은 구현하지 못했다**: 선만 있는 층과 색 층이 분리된 그림이 아니라서, 대신 **종이색 워시**(그림이 장면 배경색(종이 `#ece4d1`, 밤 `#14122b`, 노을 `#5a4562`)으로 0.45초 덮였다가 0.45초 동안 걷히며 새 그림이 나옴)를 쓴다. 이름만 표의 "스케치→채색" 자리에 대응한다.
- **배분 규칙**: 같은 전환을 연속 두 번 쓰지 않고(앞 두 번과도 겹치지 않게), 장면이 바뀔 때는 줌·워시를 더 자주, 모양 겹치기는 장면 안에서만 쓴다. 칠판 앞뒤는 하드컷. 본편 시험 배분(125장): 줌 23, 페이드 23, 슬라이드 25, 모양 겹치기 24, 워시 26, 하드컷 4.
- 전환 길이는 약 0.5초(줌은 나가는 쪽 1.1초 + 들어오는 쪽 1.7초). 전환은 앞 장면의 빈 간격(0.8초) 안에서 시작해 내레이션과 겹치지 않는다.
- 줌 전환의 휙 효과음은 9-3.
- 레퍼런스 영상(사용자 제공, 32초)에서 확인한 전환: 캐릭터 눈동자로 들어가 다음 세계가 열림, 뉴런 가지→번개, 해바라기 씨 배열→새 떼→은하→블랙홀(모양이 닮은 물체로 이어 붙임), 동심원 속으로 들어가 우주로, 흰 종이 스케치→채색, 마지막에 캐릭터로 돌아옴. 장면마다 가운데에 이어질 물체가 있었다.

## 9. 오디오

### 9-1. 참고 영상 실측 (한국어 영상)
- 참고 영상은 **배경음악이 없다**(Miya's Lab은 9-4에서 다르게 정했다). 문장 사이 무음 구간이 디지털 무음(-97dB)까지 떨어진다. 효과음도 확인되지 않았다.
- 내레이션: **남성 1인**, 기본 음높이 약 124Hz(중저음). 세 영상이 같은 목소리이고 다이내믹 레인지가 매우 좁아 **AI 음성(TTS)으로 추정**된다.
- 통합 음량 **-16.8 LUFS**, 음량 변화 폭(LRA) 3.5 LU. 고르고 차분하다.
- 말 속도 **초당 약 4.8음절**(분당 약 285음절). 낭독보다는 이야기하듯 담담하게.
- 영상 길이 19~27분, 대본 약 8,000~10,500자.

### 9-2. 영어 출력 목표
- **영어 TTS, 남성 1인, 차분한 중저음(바리톤 계열)**, 모든 영상에서 같은 목소리. 음량 목표: 내레이션 **-16.8 LUFS**, LRA 약 3.5 LU. **배경음악은 9-4 규칙대로 합성해서 깔고**, 효과음은 9-3 규칙대로 넣는다.
- **말 속도 (2026-10-10 재측정)**: Kokoro(`am_michael`, `--speed` 기본값)는 **분당 약 160~167단어(평균 약 163)**로 읽었다. 측정값: 본편 2,837단어 → 음성 1,047.0초(162.6wpm), 같은 영상의 이전 대본 2,382단어 → 863.8초(165.5wpm), 1,604단어 → 594.7초(161.8wpm), 숏츠 139단어 → 52.7초(158.4wpm), 133단어 → 47.9초(166.8wpm). **2026-10-09의 126wpm(672단어 → 320.5초)은 다시 재현되지 않았고 원인은 확인하지 못했다.** 그래서 단어 수 계산은 **분당 163단어**로 하고, 음성을 만든 뒤 반드시 실제 길이를 잰다.
- **영상 길이: 약 20분 (채널 결정, 2026-10-10 사용자 변경, 이전 10~15분)**. 허용 18~21분. 영상 길이 = 음성 길이 + 장면 사이 간격(0.8초 × 장면 수) + 앞뒤 여백 3.5초. 장면 30~35개면 간격·여백이 약 28~32초다.
- **대본 길이: 약 3,100단어, 허용 2,900~3,300단어** (163wpm 기준 음성 약 17.8~20.2분 + 간격 약 0.5분 = 영상 약 18.3~20.8분). 이전 기준(2,300~2,700단어)은 126wpm 가정이라 실제로는 약 14~17분이 된다. 에포미스 본편은 2,837단어로 17분 56초였다.
- 그림은 의미 단위당 1장이라 20분이면 약 230~260장이다(장수 제한 없음).
- **서버 렌더 시간 (실측)**: 에포미스 본편(17분 56초, 그림 226장, 효과음 큐 308개, 배경음악)이 GitHub Actions에서 **4,035초(67분, 영상 길이의 약 3.75배)** 걸렸다. 숏츠는 각 157~188초. 본편+숏츠 2편 전체 실행은 약 77분이었다. 20분 영상은 약 75분으로 추정한다. 월 무료 실행 시간 한도(프라이빗 저장소)는 확인하지 않았다.
- **최종 MP4 음량 (실측)**: 내레이션을 −16.8 LUFS로 맞춰도 효과음·배경음악을 섞은 최종 MP4는 **−17.4~−17.7 LUFS**(본편 −17.6, 숏츠 −17.4/−17.7), 피크 −1.5 dBFS였다. 목표보다 0.6~0.9 LU 낮다. 맞추려면 렌더 후 오디오만 다시 정규화하는 단계를 워크플로에 넣어야 한다(아직 하지 않음).
- 받은 대본이 이 범위를 벗어나면 12-1의 길이 조정 규칙을 따른다.

### 9-3. 효과음 (채널 결정, 2026-10-09 개정)

참고 영상에는 효과음이 없지만, Miya's Lab은 **내레이션을 가리지 않는 조용한 효과음**을 그림·전환에 **싱크**해서 넣는다. **배경음악은 9-4 규칙대로 합성해서 깐다(2026-10-10 사용자 결정으로 "넣지 않는다"를 바꿈).** 효과음은 지식 전달 영상에 맞게 작고 다양하게, 음정(띠리링)이 있는 소리는 쓰지 않는다. 장면 사건 효과음은 사건에 맞는 소리를 고르되 같은 소리를 두 컷 연속으로 쓰지 않는다(`tools/art_spec_v3.md`).

**상시 깔리는 저음(드론) 앰비언트는 쓰지 않는다 (사용자가 영상 전체에서 "웅" 소리가 들린다고 지적, 2026-10-09).** 렌더에 쓴 앰비언트 파일 분석 결과 에너지의 93%가 200Hz 아래에 있고 약 55Hz의 단일 음이 두드러졌다. 내레이션 트랙은 문장 사이가 디지털 무음이라 원인이 아니었다(렌더에 들어간 원본 파일을 분석한 것이며, 서버에서 렌더된 최종 MP4 자체는 분석하지 못했다).

**구현 상태 (2026-10-09, `tools/sfx_lib.py`, `build3.py`)**
- **효과음 v2 (2026-10-10, `tools/sfx_lib.py`)**: 사용자가 "띠리링 하는 효과음이 거슬리고 소리가 너무 크다"고 해서 다시 만들었다. 합성 소리 **25종**: swish, hush(옛 이름 shimmer는 별칭), tick, crackle, bubble, wind, bell, click, creak, drip, thud, chime, rustle, pop, pencil, page, cloth, woodblock, sand, rain, splash, step, breath, stone, flutter. **소리마다 변형 3개**(seed가 달라 같은 이름이 연달아 나와도 소리가 조금 다름, 큐마다 돌려 씀). 음정이 있는 소리(shimmer의 사인파 5음, 종, 차임)를 없애고 필터링된 잡음(shimmer→hush, 종→둔탁한 나무 소리, 차임→종이 튕기는 소리 2번)으로 바꿨고, drip·pop·bubble은 짧게 하고 저역통과로 부드럽게 했다. 전부 고역통과 150Hz, **피크 −24dBFS**(이전 −18), 스테레오 48kHz. 25종 중 5종을 샘플로 분석한 결과 100Hz 미만 에너지 비율은 모두 0.001 이하(소수점 4자리 반올림 기준). **무엇이 "띠리링"이었는지는 소리를 들을 수 없어 확정하지 못했다.** 음정 있는 소리(shimmer·bell·chime)가 가장 유력한 원인이라 이 셋을 음정 없는 소리로 바꿨다. 사용자가 새 영상을 듣고 판단한다.
- 큐 출처: 전환 → swish(줌, 슬라이드는 음량 낮게)·hush(모양 겹치기)·rustle(워시), 페이드는 무음. 포커스 → tick. 장면 사건 → 그림 사이드카 `sfx [{name, word, vol}]`(그 컷 대본의 단어에 맞춤). 같은 시각에서 0.9초 안에 겹치는 큐는 우선순위(사건 > 전환 > 포커스)로 하나만 남긴다. 에포미스 본편(18분) 큐 308개(10분당 약 17개).
- **싱크 확인**: 70초 시험 렌더 MP4의 소리에서 내레이션 파일을 빼고 남은 소리를 보니, 앞 5개 큐(9.4~20.1초)는 큐 시각 직후 0.6초 구간의 잔여 에너지가 직전보다 4~10배 컸다(0.0135→0.0031 등). 그 뒤 구간은 내레이션 재구성이 어긋나 같은 방식으로 확인하지 못했다. 큐 음량은 내레이션 대비 약 -15~-20dB(같은 잔여 측정 기준).
- **웅 소리**: 앰비언트를 없앤 시험 렌더에서 조용한 구간(0.5초 창, RMS 0.03 미만) 18개를 보니 RMS 0.0003~0.02로 일정한 저음이 없었다.

**종류**
| 구분 | 용도 | 예 |
|---|---|---|
| 전환 효과음 | 줌 전환의 가속 확대에 맞춰 점점 커지는 휙, 도착할 때 짧게 감속. 슬라이드는 짧은 스침, 스케치→채색은 부드러운 반짝임 | 휙, 스침, 반짝 |
| 포커스 효과음 | 카메라가 대상으로 확대될 때 짧게 | 낮은 틱, 숨소리 같은 짧은 소리 |
| 장면 사건 효과음 | 그림에 있는 소리를 그 장면에서만, 낮게 | 모닥불, 끓는 물, 바람, 종, 자물쇠 잠김, 삐걱 |
| 칠판 | 기존 분필 소리 유지(7-4) | 분필 |

**규칙**
1. **효과음 큐를 컷마다 만든다**: 컷의 포커스 대상, 전환 종류, 그림 속 사건에서 큐(종류, 시작 시각)를 도출한다. 시각은 화면에서 그 일이 일어나는 프레임에 맞춘다.
2. 배경 소리가 필요하면 **그 장면에서만**(불꽃, 바람, 끓는 물 등) 짧게 낮게 깔고 장면이 바뀌면 끊는다. 다음 장면에도 같은 소리를 이어 깔지 않는다. 소리 없는 장면은 무음으로 둔다.
3. 저주파(약 120Hz 아래(합성 소리는 150Hz 아래를 깎는다))를 계속 내는 소리는 쓰지 않는다. 합성 소리는 120Hz 이하를 필터로 깎는다.
4. 음량 **(제안, 실측 아님)**: 장면 소리는 내레이션보다 15~20dB 낮게, 큐 효과음은 피크 −24dBFS(2026-10-10에 −18에서 낮춤). 내레이션이 나오는 동안은 효과음을 4~6dB 더 낮춘다.
5. 내레이션 트랙의 문장 사이는 계속 무음. 효과음은 별도 트랙.
6. **금지**: 웃음소리, 비명, 과장된 코믹 효과음, 고통·사망 장면을 자극하는 소리, 출처가 불분명하거나 저작권이 있는 음원.
7. **음원은 직접 합성한 소리(저작권 문제 없음)**를 쓴다. 이 작업 환경은 외부 사이트가 막혀 무료 효과음 라이브러리를 받을 수 없고, 합성음은 실제 녹음보다 단순하다. 라이브러리 음원을 쓰려면 라이선스를 확인한 파일을 사용자가 올려 줘야 한다.
8. 효과음 큐는 HTML 장면 데이터와 대본 txt에 함께 적는다.
9. 싱크는 렌더 후 프레임과 소리 시각을 대조해서 확인한다. 소리의 자연스러움은 사용자가 직접 들어 보고 판단한다.


### 9-4. 배경음악 (채널 결정, 2026-10-10 — 9장 첫머리의 "배경음악 없음" 규칙을 대체)

사용자 요청: 저작권 문제가 없고 가사가 없으며, 내레이션을 방해하지 않고 뒤에 깔리는 잔잔하고 일관된 음악. **직접 합성한다.**

**구현 (`tools/bgm_lib.py`, `build3.py`에 연결, 2026-10-10)**
- 작곡: 4가지 코드 진행(Am-F-C-G 계열 등), 코드 하나 8초, 부드러운 패드(사인파 + 약한 배음, 좌우 미세 디튠)와 박마다 약 40% 확률로 나오는 아주 작은 플럭. 진행은 같은 것이 연달아 나오지 않게 섞는다. 영상 길이만큼 만들고(20분이면 약 150코드) 처음 3초 페이드인, 끝 5초 페이드아웃.
- 샘플·외부 음원·가사·보컬 없음. 코드와 음 선택은 코드에 있는 난수(`seed=5`)와 4개 진행뿐이라 저작권이 있는 곡을 쓰지 않는다.
- **저음 없음**: 250Hz 고역통과 + 4.5kHz 저역통과. 합성 직후 분석에서 에너지 비율이 150Hz 미만 0, 200~400Hz 56%, 400~1000Hz 37%였다(고역통과 150Hz일 때 값이며, 250Hz로 올린 뒤에는 다시 재지 않음).
- **덕킹**: 실제 내레이션 파일(`n##.wav`)에서 50ms 단위 음량 곡선을 만들어, 말이 있는 구간(−48dBFS 이상, 0.6초 이하 틈은 이어 붙임)에서는 기준 음량, 말이 없는 틈에서는 +4dB(어택 0.25초, 릴리스 1.2초)로 올린다. 이 곡선이 음악 파일에 미리 구워진다(렌더에서는 `bgm.m4a` 한 개, AAC 96kbps, 트랙 20).
- **음량**: 말하는 구간의 음악 RMS를 내레이션 RMS보다 **13dB 낮게**(`BGM_BELOW` 환경변수로 조정). 이 환경에서 10분 본편으로 잰 값: 내레이션 말 구간 −17.2dB, 음악 −30.2dB(RMS, 코드가 계산한 값), 음악만 −27.8 LUFS(LRA 2.5). 내레이션만 −16.8 LUFS → 내레이션+음악 −16.8 LUFS(차이 0.1 LU 미만), 피크 −1.5 → −0.7 dBFS(효과음 제외).
- 렌더 확인: 15초 세로 시험 렌더 MP4에 음악 트랙이 들어가고(AAC 스테레오, 내레이션 끝난 뒤 구간에서 음악 소리 평균 −25dB) 통합 −17.5 LUFS, 피크 −1.5 dBFS였다. **에포미스 본편(18분)·숏츠 2편을 음악을 넣어 서버에서 렌더했다(2026-10-10, 9-2의 최종 음량).** 음악의 크기와 느낌은 사용자가 듣고 판단한다.
- `NOBGM=1`로 음악 없이 만들 수 있다.

**규칙**
1. 내레이션이 항상 우선이다. 음악이 말 구간에서 들리더라도 가사처럼 주의를 끌지 않아야 한다.
2. 한 영상 안에서 음색·템포를 바꾸지 않는다(일관성). 진행만 바뀐다.
3. 칠판 구간에도 같은 음악이 흐른다(분필 소리는 효과음 트랙).
4. 숏츠도 같은 음악을 쓴다(길이만큼 따로 합성).
5. **음악이 마음에 들지 않는 점(너무 크다/심심하다/반복적이다)은 사용자가 영상을 듣고 판단한다.** 나는 소리를 들을 수 없고 위의 측정값만 확인했다. 조정 방법: `BGM_BELOW`(크기), `bgm_lib.py`의 진행·플럭 확률.

## 10. 대본 말투와 구조 (장면 설계 참고용)

### 10-1. 말투 **(환산)**
참고 영상은 한국어 존댓말 어미를 섞었다("-습니다/-ㅂ니다" 약 45%, "-요" 약 42%, "-죠" 약 8%). 영어에는 이런 어미가 없으므로 다음으로 대체한다.
- **대화체의 따뜻하고 공손한 톤**. 한 사람에게 이야기하듯 쓰고, 시청자를 "you"로 부른다. 축약형(it's, don't)을 써도 된다.
- **짧은 문장, 평균 15~20단어**(참고 영상의 21~28음절을 단어당 약 1.4음절로 환산). 평서문과 의문문을 섞는다.
- **수사 의문문은 영상당 8~18개** (참고 영상 7~19개, 20분 길이에 맞춤).

### 10-2. 도입 훅 (처음 60초)
1. 일상적인 감각으로 시작 — "Take a look at your fingernails." / "People who smell good…"
2. 의외의 숫자나 사실 — "3.8 cm a year", "10 trillion won"
3. 뒤집기 — "And yet that country was the filthiest in Europe."
4. 핵심 질문 — "So how did … become …?"
5. 출발 선언 — "Let's follow it from the start." / "Let's go through the first one."

### 10-3. 본문
구체적인 장면 묘사로 이야기를 연다("At 11 p.m., at an observatory on a mountaintop…"). 그다음 원리를 설명하고, 일상 비유("marking a child's height on a door frame", "pushing a swing")를 든다.

### 10-4. 결말
다시 시청자의 현재로 돌아온다("Tonight, try opening your window."). 감성적으로 정리한다.

### 10-5. 구독 요청(CTA)
주제에 맞춘 은유를 쓴다. 참고 영상 예시(번역):
- "Subscribing and liking is what lets Miya's Lab send one more beam of light into the next night."
- "…the warmest ink."
- "…so the scent lingers a little longer."

채널을 가리킬 때는 "Miya's Lab" 또는 "this lab"이라고 쓴다. 참고 채널의 "서재(library)" 표현은 쓰지 않는다.

## 11. 재현을 위한 핵심 규칙 15가지
1. 모든 장면은 **같은 화풍**(그 영상의 팔레트로 칠한 종이·밤·노을 배경, 얇은 스케치 선, 부드러운 빛, 가운데 둥근 물체)으로 만든다. 3D와 실사는 섞지 않는다(사진 삽입 예외).
2. 정지 이미지 그대로 쓰지 말고 **인물·빛 동작 그룹**을 넣고, 카메라는 **포커스 대상이 있을 때만** 정지→이동→정지로 움직인다(떠다님·먼지 입자·목적 없는 줌 없음).
3. **한 장면 = 새 그림 한 장 = 대본 의미 단위, 최대 7초.** 전환은 줌·모양 겹치기·슬라이드·스케치→채색·페이드를 섞고 같은 전환을 연속해서 쓰지 않는다(4-3).
4. 자막은 **영어, 한 줄, 흰색 굵은 둥근 폰트, 62% 검정 둥근 박스, 하단 중앙**. 강조색은 쓰지 않는다.
5. **로고는 오른쪽 위 모서리에 지름 81px, 여백 40px로 항상 고정**한다(원형 이미지만, 글자 없음).
6. **합성한 잔잔한 배경음악(가사 없음)을 내레이션 아래로 덕킹해서 깔고, 상시 저음 드론은 넣지 않는다**. 차분한 남성 **영어** 내레이션에 조용한 **효과음**을 그림·전환에 싱크해서 더한다(9-3, 9-4).
7. 숫자와 비교는 **칠판 인포그래픽**으로 보여준다. 노랑은 기준, 코랄은 대비.
8. 칠판 요소는 **내레이션 단어에 맞춰 0.1초 팝인**하고, 나머지는 정지 상태로 둔다. 팝인마다 분필 소리.
9. 칠판에는 **제목, 부제, 출처, 서명("Talking in class: / Miya")**을 매번 넣는다.
10. 도입과 결말에 **현대 일상 장면**을 넣어 시청자와 연결한다.
11. 대본의 **비유를 그대로 그림으로** 만든다.
12. 같은 장소가 이어지면 **인물·배경·색을 시트대로 유지한 새 그림**을 쓴다(구도만 바꾼 같은 그림 재사용 금지).
13. 영상 길이는 **약 20분**(내레이션 약 3,100단어, 허용 2,900~3,300단어, Kokoro 실측 분당 약 163단어 기준).
14. 대본을 받으면 **본편 산출물과 숏츠 2편**을 함께 낸다(12장, 19장).
15. 그림 위에 **대본에서 가져온 화면 텍스트**(이름 라벨, 숫자 배지, 짧은 말풍선)를 단위의 약 절반에 띄운다. 그림(SVG) 속에는 글자를 그리지 않는다(3-6).

## 12. 출력 형식 (대본을 받으면 이렇게 한다)

대본을 받으면 아래 순서로 작업하고, **최종 결과물 4가지**(MP4 · 썸네일 2장 · 자막 대본 · 제목·설명 파일)와 확인용 시안 1가지를 낸다.

| # | 산출물 | 형태 |
|---|---|---|
| 1 | 채팅 답변 | 길이 조정 내역, 사실 확인 표, 산출물 안내 (짧게) |
| 2 | **MP4 영상** | `<영상 슬러그>.mp4` (15장). 렌더에 실패하거나 시간이 너무 걸리면 그 사실을 알리고 나머지를 먼저 낸다. |
| 3 | **썸네일 이미지 2장** (서로 다른 시안 A, B) | `<영상 슬러그>_thumbnail_A.png`, `_B.png` (16장) |
| 4 | **자막 대본 텍스트 파일** (TTS 입력 전문 + 장면별 대본 + 자막 줄) | `<영상 슬러그>_script.txt` (14장) |
| 5 | **제목·설명 텍스트 파일** (제목, 설명란, 타임스탬프, 해시태그) | `<영상 슬러그>_metadata.txt` (17장) |
| 6 | HTML 애니메틱 (확인용 시안) | 아티팩트로 게시하는 단일 HTML 파일 (13장) |
| 7 | **숏츠 세로 영상 2편** (각각 MP4 + 대본 txt + 제목·설명 txt) | `<영상 슬러그>-short1`, `<영상 슬러그>-short2` (19장). 본편과 별도 렌더 |

장면별 상세 명세(12-3)는 채팅에 전부 쓰지 않고, HTML의 장면 패널에 넣는다.

### 12-1. 작업 순서
1. **언어 확인**: 한국어 대본이면 영어 내레이션으로 번역한다(0장 8번).
2. **길이 확인**: 영어 단어 수를 세고 예상 길이(단어 수 ÷ 163, Kokoro 실측 분당 약 163단어, 9-2)를 계산한다. **목표 약 20분 = 약 3,100단어, 허용 2,900~3,300단어(영상 약 18.3~20.8분)**.
   - **2,900단어 미만**: 대본 흐름(10장 구조)에 맞춰 내용을 보강해 2,900~3,300단어로 늘린다. 보강 방법은 구체적 장면 묘사, 원리 설명, 일상 비유, 확인된 관련 사례 추가다. 장면(문단)을 새로 넣으면 장면 사이 간격도 늘어난다.
   - **3,300단어 초과**: 반복과 곁가지를 덜어 3,300단어 이하로 줄인다.
   - 보강하는 사실·숫자·인명·연도는 **A등급(확인됨)만** 쓴다(아래 3단계). 웹 검색이 가능하면 확인하고 출처를 기록한다.
   - 채팅 답변에 "원래 ○단어 → ○단어, 추가/삭제한 내용"을 짧게 알린다.
   - **음성을 만든 뒤 실제 영상 길이(audio_prep 출력의 total + 장면 간격)를 다시 확인한다.** 18분 미만이면 사용자에게 알리고 보강할지 묻는다(에포미스: 2,382단어로 만든 음성이 14분 50초라 2,837단어로 보강함).
3. **사실 확인 (등급제, 사용자 결정 2026-10-10)**: 대본의 모든 사실 주장을 표로 정리한다(열: 항목 | 원문 | 등급 | 처리·근거). 확인할 수 없다고 통째로 지우지 않고 아래 등급으로 처리해서 영상이 밋밋해지지 않게 한다.
   | 등급 | 뜻 | 처리 |
   |---|---|---|
   | **A** | 출처로 확인된 사실 | 단정해서 쓴다. 가장 자극적인 A등급 사실을 앞에 배치한다(훅, 반전) |
   | **B** | 출처가 가설·추정·"의심된다"로 밝힌 내용 | "scientists suspect…", "one hypothesis is…", "researchers have proposed…"로 쓴다. 가설임을 밝히되 흥미로운 가능성으로 제시한다 |
   | **C** | 근거를 못 찾은 주장 | 지운다. 또는 "No one knows for sure", "The record is silent" 같은 **미스터리 훅**으로 바꾼다(모른다는 사실 자체가 사실이어야 함) |
   | **D** | 근거와 모순되는 틀린 주장 | 반드시 고친다. 고친 내용을 표에 표시한다 |
   - **지어내지 않는다**: 존재하지 않는 사례·연구·숫자·인용·인물을 만들지 않는다. 자극적으로 만드는 방법은 *사실의 배열*(가장 놀라운 A등급을 앞에, 반전은 확인된 사실로, 질문과 긴장감 있는 문장)이지 허구 추가가 아니다.
   - 사용자가 원문 유지를 원하지 않는 한 **A~D 처리를 반영한 내레이션**으로 만들고, 반영한 항목을 표에 표시한다. 등급 판단이 애매하면 한 단계 보수적으로(A가 아니라 B로) 쓴다.
4. **장면 설계**: 컷 나누기, 등장인물·장소 시트, 칠판 구간, 효과음 큐를 정하고, **색 팔레트를 대본 주제에서 고른다**(3-5: `config.py`의 `PAL_DEFAULT`와 장면별 `PAL`). 팔레트를 안 고르면 예전 보라·주황이 나온다(12-2, 12-3).
5. **HTML 애니메틱 제작 → 모든 장면 렌더링 확인 → 게시**(13장).
6. **대본 txt 생성 → 파일 전달**(14장). 내레이션은 HTML과 글자 하나까지 같아야 한다.
7. **썸네일 2장 제작 → 확인 → 파일 전달**(16장).
8. **MP4 렌더링**(15장). 기본은 **GitHub Actions 서버 렌더**(15-5)다. 렌더 원본(`render/<슬러그>/`)을 저장소에 올리고 서버가 렌더해 Drive로 올린다. 대화로는 MP4를 보낼 수 없다(30MiB 한도). 서버 렌더가 막히면 15-1~15-4의 이 환경 렌더나 사용자 PC 렌더로 바꾼다.
9. **제목·설명 파일 생성**(17장). 타임스탬프는 렌더된 MP4의 실제 컷 시작 시각으로 쓴다.
10. **Drive 영상별 폴더에 저장**(18장). 롱폼과 숏츠를 같은 푸시로 렌더하려면 `render/.slug`에 세 슬러그를 한 줄씩 적는다(15-5). **전부 Git으로 보낸다 (사용자 결정, 대본을 모바일로 보내 PC가 꺼져 있을 수 있기 때문)**: MP4, 썸네일 2장, 대본 txt, 제목·설명 파일을 모두 Actions가 Drive로 올린다. 썸네일·txt는 `render/<슬러그>/deliver/`에 넣어 푸시하면 워크플로가 같은 Drive 폴더로 올린다(15-5). 푸시 전에 `render/.slug`에 새 슬러그를 적어 두면 푸시만으로 렌더가 시작된다.

### 12-2. 장면 목록 (HTML 장면 목록에 표시)
| # | 시작~끝(예상) | 유형 | 한 줄 연출 |
|---|---|---|---|

- 예상 시간은 **초당 약 2.7단어(분당 163단어)**로 계산한다(9-2 실측).
- **의미 단위 = 1장면 = 그림 1장, 최대 7초**(보통 3~6초). 문장이 길면 의미가 바뀌는 곳에서 나눈다. 장면 번호는 세 자리(S001~). 장면마다 **포커스 대상, 전환 종류, 효과음 큐**를 적는다.
- 칠판은 숫자나 비교가 나오는 구간에만, 영상당 최대 10개.

### 12-3. 장면별 상세 명세 (HTML 장면 데이터·패널에 표시)
**일러스트 장면**
```
[S012] 일러스트 | 01:32~01:41 (9초)
내레이션(EN): "First, let's figure out who is doing the pushing."
자막 분할(EN): ① "First, let's figure out" ② "who is doing the pushing"
이미지 프롬프트(EN): flat 2D editorial illustration, … [scene]
모션 프롬프트(EN): subtle natural motion, slow push-in, …
카메라: slow push-in 5%
연속성: S011과 같은 관측소, 같은 인물(남, 40대, 두꺼운 외투)
효과음: 배경 바람(낮게) · 포인트 없음
```

**칠판 장면**
```
[S020] 칠판 | 레이아웃 B(행 목록) | 15:01~15:19 (18초)
제목(EN): "A Day's Length, Written in Stone"
부제(EN): "Pressed layer by layer into iron dust and mud"
행1(시작부터 표시): 2.461 billion years ago | 16.9 hours(노랑) | Moon 320,000 km away
행2(팝인 @ "1.4 billion years ago" 발화): 1.4 billion years ago | 18 hours(노랑) | 340,000 km
행3(팝인 @ "today" 발화): Today | 24 hours(노랑) | 380,000 km
결론(EN, 팝인 @ 마지막 문장): "No clocks, no calendars, yet the rocks kept the record"
출처(EN): "Banded iron formations, northwestern Australia · Sedimentary layers, northern China"
서명(EN): Talking in class: / Miya
효과음: 분필 @0.1초, 행2·행3·결론 팝인마다 분필
```

### 12-4. 일관성 유지 규칙
- 영상 맨 앞에 **등장인물 시트**를 만든다(이름 또는 역할, 나이, 외모, 의상). 시트의 문구는 **영어**로 쓰고, 모든 프롬프트에서 같은 표현을 그대로 반복한다.
- **장소 시트**도 만든다(장소명, 시대, 시간대, 주요 색). 같은 장소가 다시 나오면 영어 문구를 그대로 재사용한다.
- 숫자는 대본에 있거나 확인한 값만 쓴다. 출처가 없으면 칠판에 `Source: (needs verification)`으로 표시한다.

## 13. HTML 애니메틱 규격

최종 영상 전에 컷·자막·칠판·효과음 타이밍을 확인하는 **재생 가능한 시안**이다. 아티팩트로 게시하는 단일 HTML 파일로 만든다.

### 13-1. 화면 구성
- **스테이지**: 1920×1080 고정 크기 영역을 화면 폭에 맞춰 축소해서 보여준다. 안에 들어가는 층은 아래에서 위로 장면 그림 → 종이 질감(아주 옅게) → 로고 → 자막.
- **재생 컨트롤**: 재생/일시정지, 이전·다음 장면, 현재 시간 / 전체 길이, 장면 경계가 보이는 타임라인(칠판 컷은 초록으로 구분, 클릭·드래그로 이동), 효과음 켬/끔, 로고 불러오기, 전체화면.
- **장면 목록**: 장면 번호, 시작~끝 시간, 한 줄 연출. 누르면 그 장면으로 이동.
- **현재 장면 패널**: 내레이션 전문, 효과음 목록, 이미지·모션 프롬프트(복사 버튼).
- 키보드: Space 재생/일시정지, ←/→ 이전·다음 장면.
- 조작 화면(스테이지 밖)은 한국어, 스테이지 안은 영어만.
- 처음 열면 첫 장면의 첫 프레임과 첫 자막이 보이는 정지 상태로 시작한다.

### 13-2. 장면 그림
- 3장 새 화풍을 따른 **SVG**로 그린다(`tools/art_spec_v2.md`): 얇은 스케치 선, 종이·밤·노을 배경, 부드러운 그라데이션(`<filter>`는 금지), 가운데 둥근 물체.
- 같은 장소가 이어져도 **컷마다 새 그림**을 쓴다. 등장인물은 시트대로 같은 색과 옷을 유지한다.
- 3D, 실사, 이미지 속 글자·한글은 금지.
- 그림은 시안이며, 최종 영상에서는 12-3 프롬프트로 생성한 클립으로 교체한다는 점을 페이지 메모에 적는다.

### 13-3. 모션과 전환
- 장면 안 요소에 작은 반복 애니메이션을 준다(불꽃, 김, 물결, 흔들림, 인물의 숨쉬기·고개·팔 등, 4-1).
- 카메라: 포커스 대상이 있는 컷에서만 정지→한 번 부드럽게 이동→정지(4-1). 칠판은 카메라 없음.
- 애니메틱 HTML은 하드컷만 쓴다(전환 효과는 MP4 렌더 원본에만 있다).
- 일시정지하거나 타임라인으로 이동해도 장면 안 애니메이션이 그 시점의 모습으로 보이게 한다(컷 시작 후 경과 시간 기준).

### 13-4. 자막 타이밍
- 5장 규격 그대로 그린다.
- 각 자막 줄의 시작 시각 = 컷 길이 × (그 줄 앞까지의 단어 수 ÷ 컷 전체 단어 수). 컷 길이는 단어 수 ÷ 2.7초(9-2 실측 분당 163단어).
- **MP4용 시각은 15-2의 규칙을 따른다**(실제 음성 길이 기준, 시각 순서 검사 포함).

### 13-5. 칠판
- 7장 규격 그대로 HTML 요소로 만든다(좌표 1080p 기준).
- 팝인 시각은 그 숫자가 나오는 단어의 위치로 13-4와 같은 방법으로 계산한다.

### 13-6. 효과음
- 9-3 큐를 장면 데이터에 넣고, **브라우저 Web Audio로 합성**해서 재생한다(외부 음원 파일 없음).
- 재생 버튼을 누른 뒤부터 소리가 난다(브라우저 정책). 일시정지하면 소리도 멈춘다.
- 컷이 바뀌면 배경 효과음을 약 30ms 안에 바꾼다(하드컷). 포인트 효과음은 큐 시각을 지날 때 한 번 낸다. 타임라인으로 이동하면 그 지점부터 다시 시작한다.
- 효과음 켬/끔 버튼을 둔다.

### 13-7. 로고
- 6장 규격 위치에 둔다. 로고 파일은 페이지에서 직접 불러오게 하고(파일 선택), 그 브라우저에 기억한다.
- 파일이 없을 때는 같은 크기의 점선 원만 표시한다. 로고를 새로 그리지 않는다.

### 13-8. 음성
- 내레이션 음성은 넣지 않는다(TTS는 대본 txt로 별도 제작). 페이지 메모에 그렇게 적는다.

### 13-9. 게시 전 확인
- 모든 장면을 한 번씩 렌더링해서 스크립트 오류, 요소 겹침, 화면 밖으로 잘린 그림, 자막 길이를 확인한다.
- 게시 후 채팅에는 페이지가 무엇인지 한 문장으로만 알린다.

## 14. 대본 텍스트 파일 규격

- **파일명**: `<영상 슬러그>_script.txt` (예: `never-eat-humans_script.txt`), UTF-8.
- **머리말**(한국어 가능): 영상 제목(영어), `Miya's Lab · 내레이션 대본`, 실제 길이와 단어 수(Kokoro 음성 실측 기준), 컷 수, TTS 설정(영어, 남성 1인, 차분한 중저음, -16.8 LUFS), 원문 대비 바뀐 점(길이 조정·사실 확인 반영) 한두 줄.
- **1부: TTS 입력용 전문** — 영어 내레이션만. 장면당 한 문단, 문단 사이 빈 줄. 타임코드·메모·한글을 넣지 않아 그대로 TTS에 붙여 넣을 수 있게 한다.
- **2부: 장면별 대본** — 컷마다 아래 형식:
  ```
  [S001] 00:00.0–00:11.6 (11.6s) 일러스트
  <영어 내레이션>
  효과음: rustle @00:06.0, pop @00:07.6
  ```
- **3부: 자막 줄 분할** — 컷마다 자막 줄과 시작 시각(13-4 계산). 5장 규격(한 줄 4~8단어)대로 자르고, 이 줄이 MP4 자막과 같다.
  ```
  [S001]
  00:00.0  Take a look at your fingernails
  00:03.1  They have been growing
  ```
- 내레이션 문장은 HTML 애니메틱과 **글자 하나까지 같아야** 한다(따옴표·대시 포함).
- **TTS는 Kokoro(무료 로컬, Apache-2.0 표기)로 직접 만든다.** 컷(문단)별로 음성을 만들고, **컷 길이와 자막 시각은 만든 음성의 실제 길이로 확정**한다(`ffprobe`). 단어 수로 계산한 길이는 음성을 만들기 전의 추정값일 뿐이다. 실측 속도는 9-2(2026-10-10 기준 분당 약 158~167단어, 평균 163). 문장마다 다르므로 실제 길이를 잰다. 생성 시간: 2,837단어(33문단)를 만드는 데 약 15분이 걸렸다(이 작업 환경, 문단마다 따로 실행). `--speed` 1.2·1.3은 긴 문단에서 각각 12.6%·18.8% 짧아졌으나 들어보고 자연스러움을 확인하지는 않았다. 기본 속도(1.0)를 쓴다.
- 음성 명령: `HYPERFRAMES_PYTHON=<kokoro-onnx와 soundfile이 든 venv의 python> npx hyperframes@0.8.141 tts "<문장>" -v am_michael -o <파일>.wav`. 남성 영어 음성은 `am_michael`, `am_adam`, `bm_george`다. 처음 실행하면 설치와 음성 데이터(약 27MB) 다운로드가 필요하다. 새 작업 공간에서 `python3 -m venv <dir> && <dir>/bin/pip install kokoro-onnx soundfile`로 설치해 실제로 동작하는 것을 확인했다(2026-10-10).
- 채팅에서 파일로 전달한다.

## 15. HTML → MP4 렌더링 (최종 결과물)

MP4는 이 장대로 **별도 컴포지션**을 만들어 렌더링한다. **13장 애니메틱 HTML은 그대로 렌더되지 않는다.** 장면 그림이 13-2의 SVG 시안이면 MP4도 그 그림으로 만들어지므로, 채팅에 "SVG 그림 기준 MP4"라고 알린다. AI로 생성한 클립(3-4, 4-2 프롬프트)이 있으면 그 파일로 교체한다.

### 15-1. 도구와 검증 상태
- 도구: **HyperFrames**(`npx hyperframes@0.8.141`, Apache-2.0, GitHub `heygen-com/hyperframes`). 헤드리스 Chrome이 프레임마다 시간을 이동(seek)해 캡처하고 FFmpeg로 인코딩한다.
- **실제로 확인한 것** (샌드박스, Node 22.22, FFmpeg 6.1):
  - 3초 샘플이 H.264, 1920×1080, 30fps MP4로 렌더됨. 렌더 시간 약 8~10초(3초 영상 기준, 느린 스크린샷 방식).
  - `<audio>` 2트랙(`data-start`, `data-duration`, `data-track-index`, `data-volume`)이 AAC 48kHz 스테레오로 합쳐짐. 구간별 음량을 재서 소리가 지정 시각에 나고, 빈 구간은 무음(약 -91dB)임을 확인함. `data-volume` 값에 따른 음량 차이는 같은 음원으로 비교하지 않아서 확인하지 못함.
- **내레이션 포함 샘플 (2026-10-09)**: Kokoro 음성 2개 + 효과음 1개 + 자막 7줄 + 제목, 18.5초가 1920×1080 30fps MP4와 AAC 48kHz 스테레오로 렌더됨(23.3초 소요, 약 1.26배). 음성 구간에서 음량이 나오고(약 -25~-26dB), 음성 사이 공백과 끝 구간은 조용함(끝 구간 -91dB)을 확인함. 자막 박스 스타일(5장)이 의도대로 그려짐.
- **추가 검증 (2026-10-09)**:
  - **로고 오버레이**: 프로젝트의 로고(354×354, 투명 배경 RGBA)를 `left 1799px / top 40px / 81×81px`로 올리고 렌더한 프레임을 측정하니 로고가 x 1799~1879, y 40~120에 있었음(6장 규격과 일치).
  - **`data-volume`**: 같은 효과음을 1.0과 0.5로 넣었더니 평균 음량이 -37.6dB와 -43.6dB로 6dB 차이였음(0.5배 = -6dB).
  - **음량(중요)**: Kokoro 출력은 모노(24kHz)다. 모노 음성이 스테레오 MP4로 합쳐지면 측정 음량이 약 3 LU 커진다(모노 -24.1 LUFS가 MP4에서 -21.2 LUFS로 측정됨). **그래서 모노 상태가 아니라 스테레오로 바꾼 뒤 정규화해야 한다.** 방법은 15-2의 "음량" 항목.
  - **`--speed`**: 같은 문장(22단어)이 0.93배속 9.56초, 1.0배속 9.22초, 1.06배속 8.92초. 속도 값만큼 길이가 변하지는 않고 약 ±3~4% 변했다.
  - **전사**: `hyperframes transcribe`는 모델 다운로드가 `HTTP 403`으로 막혀 이 환경에서 실패했다.
  - **렌더 속도**: 18.5초 영상 23.3초, 20.5초 영상 25.9초(약 1.26배). 장면이 단순한(제목+자막) 컴포지션 기준.
- **11분 장편 렌더 (2026-10-09)**: 668.3초(20,051프레임), SVG 장면 2종 + 자막 284줄 + 내레이션 22컷 + 배경 효과음·휙 4회 + 로고 + 정지 노이즈 질감. **렌더 2,632초(43.9분, 영상 길이의 약 3.9배, 초당 약 7.6프레임), 파일 264MB**. H.264 1920×1080 30fps, AAC 48kHz 스테레오, **통합 -16.8 LUFS, LRA 2.4 LU, 트루 피크 -1.0 dBFS**. 장면이 단순한 샘플은 초당 약 24프레임이었으나 복잡한 SVG와 자막 수백 개가 있으면 6.5~8.1프레임으로 느려진다. 위의 자막 버그가 이 렌더에서 발견되어, 이 MP4는 최종본으로 쓰지 않았다.
- **이 환경의 새 화풍 시험 렌더 (2026-10-10)**: 115.6초 구간(칠판 1개 + 일러스트 19장)이 409초(약 3.5배)에 렌더됐고 −17.4 LUFS, 피크 −1.6 dBFS였다.
- **여전히 확인하지 않은 것**: 효과음(배경 -35 LUFS, 휙 -20 dBFS 이하)을 내레이션과 섞은 뒤의 개별 음량(구간 평균이 약 -20dB로 고른 것만 확인), 효과음을 실제 파일로 쓸 때의 라이선스, 자막 줄 시각과 실제 발음 시각의 일치도(전사 불가), 렌더 중단의 원인.
- 샘플 렌더에서 `init`이 작업 폴더 밖(`~/.agents/skills/`)에 스킬 10개를 설치했다. 사용자 컴퓨터에서 실행할 때 알려준다.

### 15-2. 컴포지션 규칙
- 폴더 하나에 `index.html`과 필요한 파일(GSAP, 폰트, 오디오, 로고)을 **모두 로컬 파일로** 둔다.
- **외부 CDN과 외부 폰트 링크를 쓰지 않는다.** 샌드박스에서 CDN 스크립트가 차단되어 렌더가 실패했다(`sub_timeline_script_failure`). GSAP는 `npm pack gsap@3.14.2`로 받은 `gsap.min.js`를 같은 폴더에 둔다.
- 루트 요소에 `data-composition-id`, `data-start`, `data-duration`, `data-width="1920"`, `data-height="1080"`을 준다. 시간 요소는 `class="clip"`과 `data-start`, `data-duration`, `data-track-index`를 준다.
- 애니메이션은 **일시정지 상태의 GSAP 타임라인 하나**로 만들어 `window.__timelines["main"]`에 등록한다. 13장 애니메틱의 CSS 키프레임·JS 타이머·`requestAnimationFrame`은 쓰지 않는다(seek 불가).
- 효과음은 Web Audio 합성 대신 **WAV/MP3 파일 + `<audio>` 요소**로 넣는다(렌더 결과에 Web Audio 소리가 들어가는지 확인하지 못함). 9-3의 큐 시각을 `data-start`로, 음량을 `data-volume`으로 옮긴다. 외부 음원은 라이선스를 확인한 파일만 쓴다.
- **SVG 필터를 쓰지 않는다.** 전체 화면 SVG `feTurbulence` 필터와 확대를 같이 쓰면 캡처 속도가 초당 3.84프레임까지 떨어졌다. 종이 질감은 **정지된 알파 노이즈 PNG 한 장**을 맨 위층에 올린다.
- 자막, 칠판, 로고는 5·6·7장 값을 그대로 쓴다.
- **내레이션은 14장의 Kokoro 음성**을 컷별 `<audio>` 트랙(`data-track-index` 0)으로 넣는다. `data-start`는 그 컷의 시작 시각, `data-duration`은 음성 파일의 실제 길이다. 사용자가 직접 만든 음성 파일을 주면 그것을 쓴다.
- **자막 시각 규칙 (2026-10-09 장편 렌더에서 발견한 버그 반영)**:
  - 컷 안의 줄 시각은 기본적으로 단어 수 비율 추정값이다. 음성의 무음 구간(`silencedetect=noise=-35dB:d=0.12`)에 맞추는 방식은 무음 구간 수와 문장 경계 수가 같을 때만 쓴다(22문단 중 7문단만 해당). 그 외에 가장 가까운 무음 구간으로 맞추는 방식을 쓰면 시각 순서가 뒤집힐 수 있다.
  - 실제로 자막 284개 중 4개(c80, c98, c222, c240)가 **끄는 시각이 켜는 시각보다 앞서**, 켜진 뒤 영상 끝까지 꺼지지 않고 다른 자막과 겹쳤다(300초 프레임에서 확인).
  - **그래서 타임라인을 만들 때 모든 자막이 `시작 < 끝`이고 다음 자막 시작 ≥ 이전 자막 시작인지 검사한다.** 어긋난 줄은 앞뒤 줄 시각 사이로 제한하거나 비례 추정으로 되돌린다. 컷 끝 시각은 컷 경계를 넘지 않는다.
  - 비례 추정의 오차는 무음 구간 기준으로 평균 0.43초(90% 지점 0.92초, 최대 2.08초)였다. 기준값이 전사가 아니라 무음 구간이므로 이 오차도 근사치다.
  - 렌더 전에 이 검사를 자동으로 돌리고, 렌더 후에는 컷 경계 근처와 영상 중후반에서 프레임을 몇 장 뽑아 자막이 한 줄만 보이는지 눈으로 확인한다.
- **자막 줄 시각**은 컷 안에서 단어 수 비율로 나눈 **추정값**이다(13-4). 음성에서 단어 시각을 뽑아 맞추는 전사는 이 환경에서 모델 다운로드가 막혀 테스트하지 못했다. 필요하면 사용자 컴퓨터나 다른 환경에서 `hyperframes transcribe`로 맞춘다.
- **음량 (검증됨)**: 내레이션 전체를 이어 붙인 파일을 **스테레오로 변환**한 뒤 ffmpeg `loudnorm` 2패스(`I=-16.8:TP=-1.5:LRA=3.5`, 1패스 측정값을 넣고 `linear=true`)로 정규화하고 48kHz로 저장한다. 컷별 파일로 다시 자른 뒤 `<audio>`로 넣는다. 샘플 결과: 정규화 파일 -16.8 LUFS(LRA 2.4), 효과음을 섞어 렌더한 MP4 -16.9 LUFS(LRA 3.2). 최종 MP4도 `ebur128`로 측정해서 확인한다(배경음악을 넣은 뒤의 최종값은 9-2).

### 15-3. 렌더 명령 (샌드박스)
```
export HYPERFRAMES_BROWSER_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome
npx --yes hyperframes@0.8.141 render
```
- 이유: Chrome 자동 다운로드가 프록시에서 403으로 막혀서, 설치된 Chromium을 지정한다(에러 메시지가 안내한 방법).
- **긴 렌더는 반드시 분리 실행한다.** 같은 도구 호출 안에서 `&`로만 띄우면 렌더가 `render_cancelled_parent_exited`로 취소된다. 완료 시 `render.done`에 `EXIT <코드> SECONDS <초>`를 쓰는 `run_render.sh`를 만들고 `setsid nohup ./run_render.sh < /dev/null > /dev/null 2>&1 & disown`으로 띄운다(이 호출 하나만 따로). `pkill -f hyperframes`는 자기 셸까지 죽이므로 쓰지 않는다. TTS 생성(`tools/tts.sh`)처럼 오래 걸리는 작업도 같은 방식으로 띄운다.
- **진행 감시**: 1분마다 `render.log`의 `"done":N`을 읽어 프레임·퍼센트·남은 시간을 표시하고, 6분 동안 N이 늘지 않으면 "멈춤"으로 알린다. 캡처가 100%가 되면 `Assembling final video`(오디오 합성·인코딩) 단계로 넘어가며 진행 값이 0으로 보이지만 정상이다.
- **중단되면 이어서 렌더할 수 없다.** 첫 11분 렌더가 9,093/20,051프레임(45%)에서 프로세스가 사라지고(로그 갱신 중지, `render.done` 없음, `ps`에 프로세스 없음) 처음부터 다시 돌려야 했다. 원인은 확인하지 못했다.
- 결과는 `renders/` 폴더의 MP4다. 렌더 후 `ffprobe`로 해상도·fps·오디오 트랙을, 프레임 몇 장으로 화면을, `volumedetect`로 구간별 음량을 확인한다.

### 15-4. 안전 원칙
- 새 도구는 **빈 폴더의 샘플**로 먼저 검증한 뒤 쓴다. 애니메틱 원본은 건드리지 않는다.
- 버전을 고정해서 실행한다(`@0.8.141`). 올릴 때는 샘플로 다시 확인한다.
- 설치·실행 시 작업 폴더 밖에 생기는 파일이 있으면 사용자에게 알린다.
- 도구 설명과 이 장이 다르면 직접 렌더해서 확인한 결과를 따른다.

### 15-5. GitHub Actions 서버 렌더 + Drive 자동 업로드 (2026-10-09 확인)

대화로 보낼 수 있는 파일은 30MiB까지고 11분 MP4는 약 264MB라서, **MP4는 서버에서 렌더해 Drive로 바로 올린다.** MP4는 대화나 GitHub를 거치지 않는다.

**구성**
- 저장소: `gequra-ship-it/Youtube-script-Daily`(비공개). 예전 이름 `ht`/`HT`에서 바뀌었다. **이 세션에 저장소가 옛 이름으로 연결돼 있으면 Actions 조회 API가 막힌다.** `list_repos`로 현재 이름을 확인하고 `add_repo`(access: push)를 새 이름으로 다시 호출한 뒤, 로컬 복제본의 `origin` 주소도 새 이름으로 바꾼다.
- 워크플로: `.github/workflows/render.yml`(이름 `render-video`). 실행 환경 `ubuntu-24.04`, 시간 한도 300분.
  - 수동 실행(`workflow_dispatch`): 입력 `slug`. `render/<slug>/` 폴더를 렌더한다.
  - 시험 실행: `render-pipeline` 브랜치에 `render/sample/**`이나 워크플로를 푸시하면 샘플을 렌더한다.
  - 단계: 체크아웃 → Node 22 → FFmpeg·rclone 설치(apt) → 서버의 Chrome 경로 지정과 **Chrome 예열**(`HYPERFRAMES_BROWSER_PATH`) → `npx hyperframes@0.8.141 render`(MP4가 안 나오면 한 번 더 시도) → ffprobe·음량 확인 → Drive 업로드(비밀값이 있을 때만).
- 렌더 원본 폴더 `render/<slug>/`: `index.html`, `gsap.min.js`, 폰트, 로고, 질감 PNG, 효과음 WAV, 배경음악 `bgm.m4a`, 컷별 내레이션(15-2 규칙대로 모두 로컬 파일). 파일마다 크기가 작아 일반 푸시로 올라간다(에포미스 본편 폴더 전체 53MB). 100MB를 넘는 파일은 일반 푸시로 올릴 수 없다.
- Drive 업로드: `rclone copyto <슬러그>.mp4 gdrive:<슬러그>/<슬러그>.mp4 --drive-root-folder-id <Video & Thumbnail 폴더 ID>`. 폴더 ID를 지정해서 그 폴더 안으로만 쓴다. 샘플은 `_ci-test/`로 올라간다(확인 후 지워도 된다).
- Drive 접속 정보: 저장소 비밀값 `RCLONE_CONF`(rclone 설정 파일 전체). 사용자가 PC에서 `rclone config`로 remote `gdrive`(종류 `drive`, scope `1` 전체 접근)를 만든 뒤 `rclone.conf` 내용을 Settings → Secrets and variables → Actions에 등록한다. 이 세션에서는 비밀값을 읽거나 설정할 수 없다. 설정 파일에는 Drive 로그인 토큰이 들어 있으므로 저장소를 비공개로 유지하고 채팅에 붙여 넣지 않는다.

**실제로 확인한 것**
- 18.5초 샘플이 서버에서 렌더됨(렌더 27초, 실행 전체 약 1분). 비밀값을 등록한 뒤 다시 돌린 실행은 업로드까지 포함해 약 2분 20초에 성공했고, **Drive 커넥터로 `Video & Thumbnail/_ci-test/sample.mp4`(679,279바이트)가 생긴 것을 직접 확인함.**
- 워크플로 파일(`.github/workflows`)도 이 세션에서 푸시됐다.
- Actions 실행 상태·단계별 결과는 인증 없이 `api.github.com/repos/<소유자>/<저장소>/actions/runs`와 그 실행의 `jobs_url`로 읽을 수 있다(세션에 저장소가 연결돼 있을 때). **실행 로그 본문은 읽을 수 없다.** 실패하면 사용자가 Actions 탭에서 실패한 단계의 로그를 복사해서 보여줘야 한다.
- **감시 방식 (사용자 결정 2026-10-10)**: 렌더 중에는 5분 간격으로 실행 상태를 확인하고, 정상이면 "정상"만 짧게 알린다. 자세한 설명은 오류가 났을 때만 한다. 끝나면 Drive 폴더의 파일 목록과 렌더 리포트를 확인한다.

**확인하지 않은 것**
- 수동 실행 버튼(`Run workflow`)은 워크플로가 `main`에 있어야 보일 것으로 예상한다. 지금은 `render-pipeline` 브랜치에만 있고 `main`에 병합하지 않았다.
- rclone 공용 클라이언트 ID가 2026년 중에 중단될 예정이라는 경고가 나왔다. 장기로 쓰려면 본인 클라이언트 ID로 바꾸고 `RCLONE_CONF`를 다시 등록해야 한다. 앱 게시 상태가 "테스트"이면 토큰이 7일마다 만료된다고 알고 있으나 설정할 때 Google 문서로 확인해야 한다.
- 비공개 저장소의 무료 실행 시간 한도(월 2,000분으로 알고 있음)는 확인하지 않았다. 20분 영상 한 편(본편+숏츠 2편)이 약 80분을 쓴다.

**오류 대응**
- 푸시 후 훅이 "푸시 안 된 커밋이 있다"고 경고하면, 얕은 복제본이 원격 추적 정보를 못 읽어서 나는 경우가 있다. `git ls-remote --heads origin <브랜치>`의 커밋 번호가 로컬 `git rev-parse HEAD`와 같으면 푸시된 것이다.
- 삭제 푸시(`git push origin --delete`)는 두 번 모두 "원격 서버가 연결을 끊었다"로 실패했다. 지워야 하는 브랜치는 사용자가 GitHub에서 지운다.
- `__pycache__` 파일이 바뀌어 커밋 확인 훅이 반복해서 경고하면 `.git/info/exclude`에 `__pycache__/`를 넣고 바뀐 `.pyc`는 되돌린다.

**사용자 PC에서 렌더하는 대안(차선, 2026-10-09)**: 렌더 폴더를 zip 4개로 나눠 PC의 Drive 폴더에 써 넣고(`render-package/`), PC의 `C:\miya-render`에 풀어 `run_render.ps1`로 렌더한다. Windows에서는 렌더를 실행해 보지 못했다. 설치 확인 스크립트 `install_render_tools.ps1`도 실행 결과를 보지 못했다.

**제작 순서 (`tools/README.md`에도 있음)**
1. `SLUG=x PLAN=1 python3 tools/build3.py` → `videos/x/plan.json`(의미 단위 목록: uid, 대본, 배경 종류, 전환, 앞뒤 대본).
2. 그림: `tools/art_spec_v3.md`(세로는 `art_spec_v3_vertical.md`), `art_spec_v2.md`, `art_spec_v4_backdrop.md`와 영상별 `art_brief.md`를 하위 에이전트에게 주고 `videos/x/art3/<uid>.svg`와 `<uid>.json`을 그리게 한다(에이전트 하나당 10~20장, 장면 단위로 나눔, 스크래치 파일은 에이전트마다 다른 폴더). 사이드카 JSON 키: `centre`, `focus`, `focus_word`, `sfx`, `labels`(화면 텍스트, 3-6). 그림 확인용 렌더는 `tools/svgshot.py`, 화면 텍스트를 얹은 확인과 검사는 `tools/labelshot.py`.
3. `SLUG=x python3 tools/build3.py` → `render/x/`. 세로는 `VERT=1`. `SEL=1,2,3`으로 일부 시험, `FALLBACK=1`은 그림이 아직 없을 때 장면 그림으로 대체(시험 전용).
4. 시험 렌더로 프레임·소리를 확인한 뒤 전체를 푸시한다.

**구조**
- 컷 하나 = `div.t`(전환용) 안의 `div.w`(카메라용) 안의 SVG. 전환은 `.t`, 포커스는 `.w`에 건다. `mv-` 그룹은 id를 클래스로 바꿔 GSAP 요요 트윈(유한 반복, seek 가능).
- SVG를 합칠 때 id에 컷 번호 접두어(`u<번호>_`)를 붙인다. SVG 필터 금지(15-2).

- **자막 줄 나누기**: 문장 단위, 줄 30자·7단어 이하(세로는 22자·4단어), 쉼표에서 우선 끊음. 모든 자막의 `시작<끝`과 오름차순을 만들 때 검사한다(통과).

- 인물 동작 `mv-` 그룹의 도구 지원은 합성 도형과 실제 렌더 생성 확인까지만이다(위 표).

- **썸네일**: 첫 영상(`never-eat-human-meat`)의 구 화풍 썸네일은 그대로 두었고, 새 영상 `never-eat-human-meat-v3`·`epomis-frog-hunter-v2`는 새 화풍 썸네일을 만들었다(16-5).

## 16. 유튜브 썸네일

영상과 **같은 화풍·팔레트·폰트**로 만들어서 채널 영상임을 한눈에 알아보게 한다. **영상 본편의 장면 그림(SVG 시안, AI 클립)을 가져다 쓰지 않고**, 대본 내용에서 호기심을 끄는 소재를 골라 **썸네일 전용 그림을 새로 그린다.** 서로 다른 소재·구도의 **시안 2장(A, B)**을 만든다. **(채널 결정)** 표시가 없는 값은 아래 확인된 공식 사양이다.

### 16-1. 규격
- **비율 16:9, 1920×1080 PNG**로 만든다 **(채널 결정)**. YouTube 도움말 기준으로 권장 해상도는 3840×2160이고 최소 폭은 640px이다. JPG, PNG를 쓸 수 있다.
- **파일 크기 2MB 이하**로 맞춘다 **(채널 결정)**. 도움말 기준 파일 크기 한도는 데스크톱 50MB, 모바일 2MB다. 모바일에서도 올릴 수 있게 2MB로 맞춘다.
- 파일명 `<영상 슬러그>_thumbnail_A.png`, `<영상 슬러그>_thumbnail_B.png`.
- YouTube 도움말 확인일 2026-10-08. 규격은 바뀔 수 있으니 갱신하기 전에 도움말을 다시 확인한다.

### 16-2. 구성
- **그림**: 3장 새 화풍(그 영상의 팔레트로 칠한 종이·밤·노을 배경, 3-5, 얇은 스케치 선, 부드러운 빛, 둥근 물체 하나). 3D, 실사, 과장된 만화 표정은 쓰지 않는다. **배경은 종이 또는 밤 하나를 골라 단순하게**(동심원·방사선 없음).
- **소재 선택**: 대본에서 가장 의외인 사실이나 뒤집기(10-2 훅 1~3번) 중 **서로 다른 두 가지**를 고른다(A, B). 큰 사물 하나 또는 상징 하나를 중심에 두고 배경 요소는 줄인다. 작은 화면에서도 읽혀야 한다.
- **상징으로 그린다**: 신체 훼손, 피, 시신, 사람 고기처럼 불쾌하거나 정책에 걸릴 수 있는 장면은 직접 그리지 않고 은유 사물(예: 구멍 뚫린 뇌, 금지 표시가 덮인 접시)로 바꾼다.
- **문구**: 영어만, **2~5단어** **(채널 결정)**. 영상 제목을 그대로 반복하지 않고 호기심을 더하는 말로 쓴다. 숫자는 대본에 있는 값만 쓴다.
- **문구 스타일**: 5장 자막과 같은 굵고 둥근 산세리프(Fredoka Bold, Baloo 2 Bold, Nunito ExtraBold 중 하나), 흰색 글자에 검정 반투명 박스 또는 굵은 검정 외곽선(종이 배경에서는 외곽선 없는 먹색 글자도 됨). 강조색은 3-2 팔레트의 램프 노랑 `#F2D27A` 또는 벽돌 빨강 `#B5483B` 중 **한 가지만** 단어 하나에 쓴다 **(채널 결정)**. 글자는 화면 왼쪽 또는 위쪽에 두고 그림의 얼굴·핵심 사물을 가리지 않는다.
- **로고**: 넣지 않는다 **(채널 결정)**. 작은 화면에서는 81px 로고가 읽히지 않고, YouTube가 채널 아이콘을 따로 보여준다.
- **안전 영역**: 영상 길이 표시가 오른쪽 아래를 덮으므로 그 모서리에는 글자와 핵심 그림을 두지 않는다.
- 이미지 속 글자는 영어만. 한글, 다른 언어, 참고 채널 이름을 쓰지 않는다. 채널명을 넣을 때는 `Miya's Lab`이다.

### 16-3. 만드는 방법
1. **그림에는 글자를 넣지 않는다.** AI 이미지 생성 도구를 쓰면 글자가 깨지므로, 그림은 글자 없이 만들고 문구는 HTML로 올려서 정확한 철자를 유지한다.
2. 그림을 만든다:
   - 이미지 생성 도구가 있으면 3-4 템플릿에 `thumbnail composition, one large subject, clear focal point, space for short text on one side`를 더해 영어 프롬프트를 쓴다.
   - 도구가 없으면 13-2처럼 SVG로 그린다.
3. HTML 한 장(1920×1080)에 그림 + 문구를 얹고, Chromium으로 PNG를 캡처한다(외부 CDN·폰트 링크 금지, 15-2와 같은 이유).
4. 확인한다:
   - 파일 크기 2MB 이하, 해상도 1920×1080.
   - 가로 320px 정도로 줄여서 문구가 읽히는지 본다.
   - 오른쪽 아래 모서리가 비어 있는지, 한글·철자 오류가 없는지 본다.
5. 채팅에는 시안별 문구와 소재가 대본의 어느 부분에서 왔는지 한 줄씩 알린다. 문구의 숫자·주장은 대본에 있는 것만 쓰고, 대본 내용이 사실과 다르면 문구에 쓰지 않는다.

### 16-4. 하지 않는 것
- 영상에 없는 내용을 약속하는 문구(제목과 다른 낚시성 문구).
- 실존 인물의 얼굴, 유명 캐릭터·로고, 폭력적이거나 선정적인 장면. YouTube는 이런 썸네일을 거부하거나 경고를 줄 수 있다고 안내한다.
- 대본에 없는 숫자와 출처.

### 16-5. 제작 확인 기록 (2026-10-08, 대본: The Deadly Science of Why You Must Never Eat Humans)
- A: 구멍 뚫린 뇌 + "YOUR BRAIN BECOMES A SPONGE" (대본의 Spongiform Encephalopathy 설명에서). B: 금지 표시가 덮인 접시와 포크·나이프 + "100% FATAL" (대본의 치사율 100% 설명에서).
- 두 장 모두 1920×1080 PNG, 0.71MB / 1.07MB(2MB 이하). 가로 320px로 줄여도 문구가 읽힘을 확인. 본편 장면 그림은 쓰지 않았고, 글꼴은 로컬 Fredoka Bold(npm `@fontsource/fredoka`).
- 제작 방법: SVG 그림 + HTML 문구를 Chromium으로 캡처. 외부 CDN 없이 로컬 파일만 사용.

## 18. 저장 위치 (Google Drive, 영상별 폴더)

- **위치**: Google Drive `유튜브 자동화 / Video & Thumbnail /` 아래.
- **영상마다 폴더 하나**를 만든다. 폴더 이름은 영상 슬러그(영어 소문자, 하이픈. 예: `never-eat-humans`). 여러 영상의 파일이 섞이지 않도록 **루트에 파일을 직접 두지 않는다.**
- **폴더 안 파일** (모든 파일 이름이 같은 슬러그로 시작):
  ```
  <slug>/
    <slug>.mp4
    <slug>_thumbnail_A.png
    <slug>_thumbnail_B.png
    <slug>_script.txt
    <slug>_metadata.txt
    <slug>_render_report.txt
    short/
      <slug>-short1.mp4, <slug>-short1_script.txt, <slug>-short1_metadata.txt, <slug>-short1_render_report.txt
      <slug>-short2.mp4, …
  ```
- 저장하기 전에 폴더 이름이 이번 영상의 슬러그인지, 같은 폴더에 다른 영상의 파일이 없는지 확인한다.
- **실제 영상으로 확인**: `never-eat-human-meat` 폴더에 파일 6개(MP4, 썸네일 2, 대본, 메타데이터, 렌더 리포트)가 Actions로 올라왔다. `epomis-frog-hunter-v2` 폴더에는 위 구조대로 본편 6개 + `short/` 8개가 올라왔다(2026-10-10). 이 방식이 기본이다.
- **저장 방법과 검증 상태 (2026-10-09)**:
  - Drive 커넥터로 폴더를 만드는 것은 확인했다(`Video & Thumbnail` 아래 `never-eat-humans` 생성).
  - Drive 커넥터의 파일 업로드는 base64 문자열을 직접 넣어야 해서 이미지·MP4에는 현실적이지 않다. 쓰지 않는다.
  - **PC가 연결된 세션에서는** Google Drive for Desktop의 동기화 폴더 `G:\내 드라이브\유튜브 자동화\Video & Thumbnail\<slug>\`에 파일을 쓸 수 있다(폴더 접근을 사용자가 승인해야 함). 썸네일 2장을 이 경로에 쓰는 데 성공했고, 약 1분 안에 Drive 클라우드의 같은 폴더에 같은 크기(706,303 / 1,069,268바이트)로 나타나는 것을 커넥터 검색으로 확인했다. 이 폴더의 목록과 렌더 리포트를 읽어서 업로드 결과를 확인할 수 있다.
  - **MP4는 Actions가 Drive로 올린다**(15-5). 아래 한도는 대화·PC 쓰기 도구로 MP4를 보낼 때의 이야기다.
  - **MP4 크기 한도**: 18분 영상 MP4가 611MiB였다. PC 쓰기 도구(`device_commit_files`)는 설명상 파일당 30MB, 호출당 100MB 한도라서 이 방법으로는 MP4를 보낼 수 없다(설명 기준, 직접 시도하지는 않음). 대화로 전달하는 방법(`SendUserFile`)의 크기 한도도 확인하지 못했다.
  - PC가 연결되지 않은 세션(모바일 등)에서는 파일을 대화로 전달하고, PC가 연결되면 같은 폴더에 저장한다고 알린다.
